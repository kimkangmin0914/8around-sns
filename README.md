# 단풍

## 1. 프로젝트 개요 및 배포 URL

단풍은 짧은 글을 올리고, 댓글과 답글로 대화하며, 관심 있는 사람을 팔로우하는 SNS입니다. 글과 공개 프로필은 로그인하지 않아도 읽을 수 있습니다. 글을 남기거나 다른 사람을 팔로우하려면 가입과 프로필 설정이 필요합니다.

**[단풍 사용하기](https://frolicking-muffin-3c6498.netlify.app)** · [GitHub 저장소](https://github.com/kimkangmin0914/8around-sns)

### 직접 사용해 보기

1. **가입하고 글 쓰기**에서 이메일과 비밀번호로 가입한 뒤 사용자명, 표시 이름, 소개를 입력합니다. 사용자명이 겹치면 계정을 다시 만들지 않고 이름만 바꿔 저장합니다.
2. **전체 글**에서 글을 게시합니다. 새로고침한 뒤에도 같은 글이 남아 있는지 확인할 수 있습니다.
3. 다른 브라우저나 시크릿 창에서 별도 계정으로 로그인합니다. 첫 계정의 글에 댓글을 남기고, 첫 계정으로 돌아와 **답글 쓰기**를 누르면 대화를 이어갈 수 있습니다.
4. **사람들**에서 프로필을 방문해 팔로우합니다. **내 프로필 → 팔로잉**과 상대 프로필의 **팔로워**에서 같은 관계를 확인하고 해제할 수 있습니다.

가입 후에는 자동으로 로그인됩니다. 별도로 로그인을 확인하려면 로그아웃한 뒤 같은 이메일과 비밀번호로 다시 접속하면 됩니다. 같은 브라우저의 일반 탭끼리는 로그인 정보가 공유될 수 있으므로 두 계정은 분리된 창 환경에서 확인해 주세요.

이 앱은 8around 과제용입니다. 현재 이메일 소유권 확인과 메일을 통한 비밀번호 복구를 제공하지 않습니다. 다른 서비스에서 사용하는 비밀번호를 재사용하지 말고, 글과 프로필에 민감한 개인정보를 입력하지 말아 주세요. `[점검]`으로 표시한 글과 댓글은 동작을 확인하며 남긴 자료입니다.

## 2. 로컬 실행 방법

로컬 실행은 **내 컴퓨터에서 웹 앱을 켜는 것**을 뜻합니다. 계정과 글은 온라인의 Supabase에 저장하므로 인터넷 연결이 필요합니다. Docker나 PostgreSQL을 컴퓨터에 따로 설치하지 않습니다.

### 준비할 것

[Node.js](https://nodejs.org/en/download)의 **24 LTS**와 [Git](https://git-scm.com/install/)을 설치합니다. Node.js에는 패키지 설치 명령인 npm이 함께 제공됩니다. 터미널에서 다음 명령으로 설치를 확인할 수 있습니다.

```bash
node --version
npm --version
git --version
```

Codespaces를 이미 사용한다면 그곳의 터미널에서 같은 절차를 진행할 수 있습니다. 로컬 PC가 앱 실행을 감당하기 어려울 때의 대안이며, 무료 사용량은 본인 계정에서 확인해야 합니다.

### 소스 받기

새 폴더에서 다음 명령을 한 줄씩 실행합니다. 이미 소스를 받았다면 다시 복제하지 않고 기존 폴더로 이동합니다.

```bash
git clone https://github.com/kimkangmin0914/8around-sns.git
cd 8around-sns
npm ci
```

`npm ci`는 `package-lock.json`에 기록된 버전으로 필요한 라이브러리를 설치합니다. 설치가 끝나기 전에는 다음 명령을 실행하지 않습니다.

### 계정과 글을 저장할 곳 준비하기

직접 재현할 때는 [Supabase](https://supabase.com/)에 본인의 과제용 프로젝트를 만듭니다. 다른 서비스가 사용 중인 DB를 재사용하지 않습니다.

**새 프로젝트에서만**, Supabase의 **SQL Editor → New query**에 [`202609170001_initial.sql`](supabase/migrations/202609170001_initial.sql) 전체를 넣고 한 번 실행합니다. 이 파일은 사용자 프로필, 글, 댓글, 팔로우를 저장할 표와 접근 규칙을 만듭니다. DB 구조를 파일로 남기는 방식을 *마이그레이션*이라고 합니다.

이미 이 앱에 연결해 사용 중인 프로젝트라면 초기 SQL을 다시 실행하지 않습니다. 같은 이름의 표가 있다는 오류가 나도 삭제하거나 초기화하지 말고, 적용 이력부터 확인합니다.

인증 설정에서는 **신규 가입 허용**과 **Email 제공자**를 켜고, **Confirm Email**과 **익명 로그인**은 끕니다. 현재 앱은 확인 메일을 기다리는 흐름을 제공하지 않기 때문입니다. 로그인 시도 등을 제한하는 기본 보호 설정은 그대로 둡니다. 메뉴 위치가 바뀌면 [Supabase 인증 설정 안내](https://supabase.com/docs/guides/auth/general-configuration)에서 같은 설정 이름을 찾을 수 있습니다.

### 앱에 연결 정보 넣기

프로젝트 폴더의 `.env.example`을 복사해 같은 위치에 `.env.local`을 만듭니다. 이미 파일이 있다면 덮어쓰지 않습니다. 아래 두 항목을 본인의 Supabase 프로젝트 값으로 바꿉니다.

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

첫 항목은 **Data API의 프로젝트 URL**, 두 번째는 **API Keys의 publishable key**입니다. 키는 `sb_publishable_`로 시작해야 합니다. DB 비밀번호나 `secret`·`service_role` 키를 넣지 않습니다.

이 두 값은 앱이 연결할 곳을 알려 줍니다. 글을 쓸 수 있는지는 별도로 로그인 정보와 DB 규칙이 결정합니다. 실제 `.env.local`은 Git에서 제외되며, 다른 사람에게 파일째 보내지 않습니다.

### 실행하기

```bash
npm run dev
```

브라우저에서 `http://localhost:3000`을 엽니다. Codespaces에서는 **Ports의 3000번 전달 주소**를 사용합니다. 종료할 때는 터미널에서 `Ctrl+C`를 누릅니다. 앱을 종료해도 Supabase에 저장된 자료는 지워지지 않습니다.

`npm run dev`가 사용하는 `0.0.0.0` 설정은 Codespaces의 포트 전달에도 대응하기 위한 것입니다. 로컬 공유 네트워크에 개발 서버를 공개하지 않으려면 다음처럼 주소를 제한해 실행할 수 있습니다.

```bash
npx next dev --webpack --hostname 127.0.0.1
```

화면은 열리는데 글을 불러오지 못한다면 `.env.local`의 두 값, Supabase 프로젝트의 활성 상태, 초기 SQL 적용 여부를 차례로 확인합니다. 설정을 바꾼 뒤에는 앱을 다시 실행합니다. Windows PowerShell에서 `npm.ps1` 실행 제한이 나면 `npm.cmd ci`, `npm.cmd run dev`로 실행할 수 있습니다.

## 3. 기술 스택 선택 이유

**Next.js와 TypeScript**로 화면과 서버 처리를 한 프로젝트에 두었습니다. 글 작성에서 화면과 저장 처리를 함께 따라갈 수 있고, 수정할 저장소를 여러 개로 나누지 않아도 됩니다. TypeScript는 코드에서 잘못된 형태의 값을 사용하는 실수를 찾는 데 도움을 줍니다. 외부 입력과 로그인 확인은 서버에서 별도로 수행합니다.

**Supabase Auth와 PostgreSQL**을 사용해 로그인과 데이터 저장을 연결했습니다. 인증 기반을 직접 만드는 대신, 이 앱에 필요한 작성자 확인과 데이터 접근 규칙을 구현하는 데 집중했습니다. 내 컴퓨터가 꺼져도 저장된 글은 온라인 DB에 남습니다.

**Tailwind CSS, shadcn/ui의 Radix 기반 Button, Lucide, Pretendard**를 화면 구성에 사용했습니다. 필요한 부품만 가져오고 상단 탐색, 작성자와 본문의 정렬, 댓글 연결선은 앱에 맞게 구성했습니다. Pretendard는 앱이 직접 제공하므로 외부 글꼴 서버에 매번 요청하지 않습니다.

공개 앱은 **Netlify**에서 실행하도록 구성했습니다. 개발 중 사용하는 Codespaces 주소를 제출 주소로 쓰지 않습니다. 설치한 정확한 버전은 [`package.json`](package.json)과 [`package-lock.json`](package-lock.json), 출처와 라이선스는 [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md)에 있습니다.

## 4. 하네스 구성: 고친 뒤에도 다시 확인할 수 있도록

여기서 **하네스**는 코드를 바꿀 때 같은 규칙과 검사로 확인할 수 있게 준비한 작업 환경을 뜻합니다. 예를 들어 글의 길이 제한을 바꾸더라도, 공백 글이나 다른 사람 명의의 글까지 저장되도록 바뀌어서는 안 됩니다. 이런 실수를 변경 직후 찾는 데 목적을 두었습니다.

| 준비한 것                              | 사용하는 이유                                                                      |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| `AGENTS.md`와 `IMPLEMENTATION_PLAN.md` | 구현할 범위, 데이터 보호 규칙, 실제 검사 방법을 함께 읽도록 했습니다.              |
| `DESIGN.md`                            | 글자, 색, 간격과 화면 상태를 한곳에서 정해 화면마다 기준이 달라지지 않게 했습니다. |
| `npm run check`                        | 코드 형식, 의심스러운 코드, 타입과 작은 기능의 테스트를 순서대로 확인합니다.       |
| `npm run build`                        | 현재 소스가 배포 가능한 형태로 만들어지는지 확인합니다.                            |
| `npm run test:access`                  | 준비한 두 계정으로 실제 DB의 저장·조회·권한을 확인합니다.                          |
| GitHub Actions                         | `main`의 변경과 PR에서 설치·`check`·빌드를 같은 순서로 실행합니다.                 |
| `docs/verification.md`와 `exports/`    | 실제 확인 결과와 AI 작업 기록을 남겨 설명과 실행을 대조할 수 있게 했습니다.        |

일반적인 코드 수정 후에는 다음 두 명령을 실행합니다.

```bash
npm run check
npm run build
```

`check` 안의 일부 테스트는 서버나 DB의 응답을 대신 만들어 코드의 분기를 검사합니다. **이 테스트와 빌드가 통과했다고 실제 가입이나 DB 권한까지 확인된 것은 아닙니다.** 공개 사이트의 사용 흐름은 브라우저에서 따로 확인합니다.

`test:access`는 실제 글 2개와 댓글 2개를 추가하며, 두 점검 계정 사이에 팔로우가 없으면 관계 1개도 만듭니다. 기존 데이터를 지우거나 자동으로 청소하지 않습니다. 따라서 승인한 과제용 프로젝트와 두 계정을 준비한 뒤에만 실행합니다. 필요한 설정은 [실제 접근 검사 안내](docs/verification.md#access-check-setup)에 분리했습니다.

설계·검토에는 ChatGPT, 구현과 검사에는 **OpenAI Codex**를 사용했습니다. 디자인 작업에는 Oh My Design의 세 스킬 지침을 읽고 적용했습니다. 전용 스킬 실행이나 별도 전문가 에이전트가 수행한 일처럼 표시하지 않았습니다. 사용 도구는 [`tool.md`](tool.md), 실제 대화 파일의 읽는 순서는 [`exports/README.md`](exports/README.md)에 정리합니다. 대화 요약을 원본 기록 대신 제출하지 않습니다.

## 5. 구현 중 내린 결정과 트레이드오프

### 가입 계정과 공개 프로필을 나눴습니다

가입은 됐지만 원하는 사용자명이 이미 사용 중일 수 있습니다. 이때 계정을 새로 만들게 하지 않고, 같은 계정에서 프로필 설정만 다시 시도하도록 했습니다. 이메일과 비밀번호는 다른 사람이 읽는 프로필에 포함하지 않습니다. 대신 현재 버전에서는 최초 설정 후 프로필을 수정할 수 없습니다.

### 버튼을 숨기는 데서 끝내지 않았습니다

글을 쓸 때 작성자는 화면이 보낸 이름이 아니라 서버가 확인한 로그인 사용자로 정합니다. DB에서도 사용자별 접근 규칙인 **RLS**와 입력 가능한 항목을 제한했습니다. 화면을 거치지 않는 요청에도 다른 사람 명의의 글을 저장하지 못하게 하기 위해서입니다.

팔로우는 A→B라는 관계를 한 번만 저장합니다. A의 팔로잉과 B의 팔로워는 그 같은 관계를 읽습니다. 별도 숫자를 따로 저장하지 않아 목록과 숫자를 맞춰 관리할 부담을 줄였습니다.

### 서버가 확인한 뒤 성공을 표시합니다

저장이 성공했다는 응답을 받기 전에는 작성 내용을 지우지 않습니다. 응답이 끊기면 저장 여부를 단정하지 않고, 초안을 남긴 채 목록을 다시 확인할 수 있게 했습니다. 화면에서 자동으로 글을 재전송하지는 않습니다. 다만 사용자가 다시 게시하면 같은 글이 중복될 가능성은 남아 있습니다.

### 대화와 목록의 범위를 제한했습니다

게시글과 댓글은 앞뒤 공백을 정리한 뒤 500자까지 받습니다. 내부에서는 Unicode 코드 포인트로 세므로, 일부 합성 이모지는 화면에 하나로 보여도 여러 자로 계산될 수 있습니다. 폼을 보낼 때 달라지는 줄바꿈은 같은 형태로 맞춰 화면과 서버의 계산 차이를 줄였습니다.

답글은 댓글에 한 단계까지 달 수 있고, 답글의 답글은 받지 않습니다. 서로 다른 게시물의 댓글이 부모로 연결되는 것도 막습니다. 목록은 20개씩 나누어 읽습니다. 그 사이에 새 글이 추가되면 페이지 경계에서 같은 글을 다시 볼 수 있으며, 실시간 갱신이나 읽던 목록의 완전한 고정은 제공하지 않습니다.

### 실행 구성을 작게 유지했습니다

개발 앱과 공개 앱은 같은 과제용 Supabase 프로젝트에 연결합니다. 설정을 줄인 대신 개발과 공개 데이터가 분리되지는 않습니다. 그래서 테스트에서 DB 초기화나 일괄 삭제를 하지 않습니다. 무료 서비스의 한도나 프로젝트 일시정지가 접속에 영향을 줄 수 있다는 점도 남아 있습니다.

이메일 확인과 메일 기반 계정 복구, 글·댓글의 수정·삭제, 이미지 업로드, 좋아요, 알림은 구현하지 않았습니다. 없는 기능을 버튼만 만들어 표시하지 않습니다.

## 6. 시간이 더 있었다면 개선했을 부분

**디자인을 더 다듬고 싶습니다.** 긴 글과 여러 답글을 휴대폰에서 읽을 때 간격이 답답하지 않은지, 작성과 취소 버튼을 찾기 쉬운지 실제 사용자와 확인하고 조정하겠습니다. 화면마다 별도의 장식을 더하기보다는 읽고 대화하는 과정이 편해지는 쪽을 우선하겠습니다.

**계정을 다시 찾고 정보를 고치는 기능을 보완하고 싶습니다.** 이메일 확인과 비밀번호 복구, 프로필 수정이 있으면 오기입이나 비밀번호 분실 뒤에도 서비스를 계속 사용할 수 있습니다. 실제 사용자 자료를 다루기 시작한다면 탈퇴와 데이터 삭제도 함께 설계해야 합니다.

**통신이 끊겨도 안심하고 게시할 수 있게 만들고 싶습니다.** 같은 작성 요청을 다시 보내도 글이 중복되지 않도록 처리하고, 새 글이 올라오는 중에도 읽던 목록을 더 안정적으로 이어갈 수 있게 개선하겠습니다.

실행별 결과와 아직 확인하지 못한 항목은 [검증 기록](docs/verification.md)에 남깁니다. 현재 CI 결과는 [GitHub Actions](https://github.com/kimkangmin0914/8around-sns/actions/workflows/ci.yml)에서 확인할 수 있습니다.
